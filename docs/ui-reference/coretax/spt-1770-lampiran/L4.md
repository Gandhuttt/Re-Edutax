>    `calculateL4B9` carry three extra branches: spouse neto ≤ 0 puts the *whole*
>    PPh gabungan on the WP with no ratio; WP neto < 0 gives the WP a 0 share; and
>    spouse neto < 0 forces the spouse share to 0 rather than `gabungan − WP`.
>    Both measured cases were 75/25 splits with positive values, which exercise
>    none of them.

## Section B feeds back into Induk's PPh Terutang chain — critical, changes Induk's formula for any PH/MT taxpayer

**Confirmed 2026-08-18, same draft.** With Induk row 7 = PH and L-4 Section B
filled (WP neto-after 600.000.000, Istri neto-after 200.000.000, PTKP
gabungan unset so gabungan split was 138.000.000 WP / 46.000.000 Istri),
Induk's own Section C changed:

| Row | Before (row 7 blank, no PH/MT) | After (row 7 = PH, L-4 B filled) |
|---|---|---|
| 6, Penghasilan Kena Pajak | `600.000.000` (= row 4 − row 5) | **`0`** — bypassed entirely, despite row 4 still showing 600.000.000 and row 5 (PTKP) still `-/-` (0) |
| 7, PPh Terutang | `124.000.000` (bracket formula on row 6) | **`138.000.000`** — exactly L-4 Section B's "PPh terutang yang ditanggung oleh Wajib Pajak", not a bracket calculation on anything in Induk itself |
| 8, Apakah terdapat pengurang PPh Terutang | Ya/Tidak, previously Ya with 0 | still Ya, still 0 (unrelated to this change, coincidental prior state) |
| 9, PPh Terutang setelah pengurang | `124.000.000` | `138.000.000` |
| 11a onward | (124.000.000-based) | **propagates correctly**: 11a = 137.999.999 = 9−10a−10b−10c+10d = 138.000.000−0−0−1+0 |

So for a PH/MT taxpayer, Induk row 6 is not computed from row 4 − row 5 at
all: the real PPh Terutang comes from the joint-then-split calculation in L-4
Section B, and row 6 is left at 0 (or possibly hidden/disabled entirely, not
confirmed which) as a signal that the individual PKP path doesn't apply.

**Second test, retracted after review.** Cleared 13b by setting 13a = Ya, and
Induk row 7 stayed at 138.000.000 instead of reverting to 124.000.000. I
originally read this as "the override is driven by PH/MT alone, independent
of 13b." **That conclusion is unsound and is retracted.** This draft's L-4 tab
and its Section B data were materialized earlier in the same session (13b was
Ya when Section B was filled in), and this file's own earlier notes
(`../spt-1770-induk/HINTS.md`, "Ya answers materialise lampiran tabs,
irreversibly") already establish that Coretax does not retract a
tab/section's data or effects just because the triggering answer is later
switched off. The second test therefore only re-confirms that already-entered
data keeps being used, it does **not** show Section B (or its override) is
reachable, or ever applies, on a draft where 13b was never set to Ya. The
simpler, uneliminated hypothesis is that Section B's data-entry UI, like on
our build, only exists behind 13b = Ya, exactly as this app already gates it,
and the override is real but conditioned the same way our L-4 tab already is.
**Not a gap in the implementation.** Would need a genuinely fresh draft
(PH/MT set, 13b never touched) to rule this out for certain, but there's no
standing reason to believe the untested hypothesis over the simpler one.
